## 1. Executive summary

This is an ambitious, heavily instrumented system. It has more defensive thinking than most retail trading code: a fail-closed validator, a journal with a hash chain, reconciliation, readiness gates, and a test suite of 4,300 tests that mostly passes on a platform it was never built for. The previous audit's fixes are real; I re-verified several of them.

The main problem is that **the safety design is better than its wiring**. Several controls look correct in isolation and are well tested, but don't hold at the seams between modules:

| # | Finding | Severity |
|---|---|---|
| C1 | **25 modules load twice under two names.** The news feed and the decision graph each have their own kill-switch latch, so a news-triggered latch never reaches the trading decisions. | 🔴 |
| C2 | **The API control plane has no authentication and CORS allows every origin.** Any web page in the operator's browser can start the engine, approve strategies as "operator", move strategies between stages, and add or delete accounts. | 🔴 |
| C3 | **The deck's MT5 tool palette sends raw `order_send` to the broker on Enter.** There is no confirmation, and the order skips the validator, risk manager, kill switch, autonomy level and journal. | 🔴 |
| C4 | **Emergency controls do nothing.** `flatten` and `killswitch` are logged as `CONTROL_EXECUTED` but never applied, and the autonomy gate is skipped if any monitoring call throws. | 🟠 |
| C5 | **A credential-shaped secret in a public repo:** `tests/test_section_f_hardening.py:20`. | 🟠 |
| H1 | Risk manager mixes local and UTC dates. In IST, a restart between 00:00 and 05:30 resets the daily loss limit. | 🟠 |
| H2 | Stage timeouts are declared but never enforced; the `degrade` → hold-only policy is never read. | 🟠 |
| H3 | `core/strategy_trial_ledger.py` is missing. The readiness check silently uses a stub that always reports `valid`. | 🟠 |
| H4 | The validator approves when its inputs are absent: five gates default to *pass*, and the minimum stop distance defaults to 0. | 🟠 |
| H5 | The performance statistics the LLM and promotion gates rely on are inflated: Deflated Sharpe with 1 trial, ×√252 on per-pulse returns, no out-of-sample split in the genetic alpha miner. | 🟠 |
| H6 | The live order path has the lowest test coverage: `order_execution.py` 40 %, `market_data_provider.py` 54 %. | 🟠 |
| H7 | Monolith hotspots: `main()` is 4,362 lines and `execute_cycle()` 2,039. Trading, training, news triage and RL share one process, which matches the documented torch crashes below 1.5 GB free RAM. | 🟠 |

**Top five fixes, in order.** Each is small and removes a whole class of risk:
1. **One import root.** Delete the `sys.path` inserts (88 sites) and import as `core.x` / `data.x` everywhere. This fixes C1 and every other duplicated singleton (§2.1, §5).
2. **Auth on the API.** A per-install token header, an origin allowlist and a `Host` check (§2.2).
3. **One order gateway.** Every order, including UI and MCP orders, goes through `validate → size → journal → send`. Make the deck's `mt5_order_send` read-only, or route it through the gateway (§2.3).
4. **Make emergency controls real.** Implement flatten and killswitch, and make the autonomy gate fail closed (§2.4).
5. **Use UTC everywhere** for risk rollovers (§3.1), and enforce stage deadlines with a future and a timeout (§3.2).

## 2. Critical findings

### 2.1 🔴 C1: Core modules load twice. The kill-switch latch is split in two.

`mt5_trader.py:52-55` (and 87 other sites) put `core/`, `intelligence/`, `operations/`, `research/`, `data/` and `ui/` on `sys.path`. Code then imports the same file both ways: 2,437 package-style imports and 1,000 bare ones. **142 modules are imported both ways.** Python treats `kill_switch_latch` and `data.kill_switch_latch` as different modules: separate objects, separate globals, separate locks, separate singletons.

Importing `mt5_trader` alone produces **25 double-loaded production modules**, including:

```
core/trading_safety.py      -> trading_safety, core.trading_safety
core/risk_manager.py        -> risk_manager, core.risk_manager
data/kill_switch_latch.py   -> kill_switch_latch, data.kill_switch_latch
data/llm_router.py          -> llm_router, data.llm_router          (two _router singletons)
data/market_data_provider.py-> market_data_provider, data.market_data_provider (two server-offset caches)
intelligence/trading_memory.py, operations/agent_operations.py, operations/strategy_lifecycle.py, …
```

**Proof that this breaks the kill switch:**

```
news ingest   data/realtime_news_ingest.py:30   from kill_switch_latch import get_kill_switch_latch   (bare import first)
decision path intelligence/graph_nodes.py:46     from data.kill_switch_latch import get_kill_switch_latch
runtime:      rni.get_kill_switch_latch() is graph_nodes.get_kill_switch_latch()  ->  False
```

`KillSwitchLatch` treats in-memory state as authoritative (`data/kill_switch_latch.py:108`) and reads the file only in `__init__`. So:
- A confirmed news tripwire latches copy A (`observe`). The decision graph checks copy B (`graph_nodes.py:442`), which stays unlatched.
- Copy B's `apply_market_data()` calls `_save()`, which writes its *unlatched* state over the file. A restart then can't recover the latch either.

The latch has 94 % test coverage, yet this is invisible to the tests, because they only ever import it under one name.

The same mechanism affects every module-level singleton or cache among the 25. `isinstance` checks across the two copies also fail, because the class objects differ.

**Fix:** a single import root, plus a guard test that imports `mt5_trader` and `ui.gui_api` and fails if any repo file appears twice in `sys.modules`. The check from this audit is about 15 lines and can become that test.

### 2.2 🔴 C2: The API control plane can be driven by any website

`ui/gui_api.py:86-90`: `allow_origins=["*"], allow_methods=["*"], allow_headers=["*"]`, with no authentication on any route. Binding to `127.0.0.1` (`:3414`) does **not** protect a localhost API from the operator's own browser. With wildcard CORS, a script on any page can make credentialed-free JSON requests to `http://127.0.0.1:8000` and read the responses. DNS rebinding works too, since `Host` isn't checked. Routes that can be reached this way:

| Route | Effect |
|---|---|
| `POST /api/control/start` (`:487`) | Spawns an engine with any symbol, model, risk and `--live`. Live still needs `REQUIRE_LIVE_CONFIRMATION` in the API server's environment, but if the operator runs live, that is set. |
| `POST /api/control/approve` (`:1523-1531`) | Writes an APPROVED strategy decision with `actor` taken **from the request body** (defaults to `"operator"`). |
| `POST /api/control/strategy_stage` | Moves any strategy to any stage. |
| `POST/DELETE /api/config/accounts` (`:607`, `:703`) | Vaults new credentials, switches the default account, deletes accounts. |
| `POST /api/internal/update` (`:424`) | Overwrites the UI's balance, equity and log state, so the operator can be shown false numbers. |

**Fix:** generate a token at install time (the `mt5_bridge.key` pattern already exists) and require `Authorization: Bearer` on every mutating route and WebSocket. Restrict CORS to the deck/GUI origin. Reject requests whose `Host` isn't `127.0.0.1:8000` or `localhost:8000`. Give `/api/internal/update` its own secret.

### 2.3 🔴 C3: An unguarded order path from the deck to the broker

`tui_opentui/src/screens/MT5Screen.tsx:510` lists `mt5_order_send` in the TRADING tool group. `run()` (`:544-563`) parses free-form JSON and calls it on Enter. The only safeguard is a "⚠" in its label. These orders go straight from `metatrader5-mcp` to the terminal and bypass **everything**: `DeterministicValidator`, `RiskManager`, the kill switch, the autonomy level, margin preflight and the journal. Daily reconciliation would later flag them as out-of-band trades.

**Fix:** the deck must never hold an order-capable tool. Expose `mt5_order_check` (dry run) only. If manual orders are wanted, add a `POST /api/orders/manual` that goes through the same validator and journal and requires a typed confirmation (symbol plus volume).

### 2.4 🟠 C4: Emergency controls report success but do nothing

- `operations/autonomy.py:244-245`: `flatten` and `killswitch` only record `CONTROL_ACK_QUEUED`.
- `intelligence/llm_orchestrator.py:7361-7367` drains them and emits **`CONTROL_EXECUTED`**. No positions are closed and no kill switch is set. The operator sees "executed".
- The whole block that holds the autonomy gate (`:7349-7384`) sits inside `try … except Exception: log.debug(...)`. If anything earlier in it throws (supervisor heartbeat, guardian progress, drain, metrics export), the check at `:7368-7371` is skipped, the exception is logged at **debug** level, and the cycle trades.

**Fix:** implement `flatten` (close every position owned by this magic number, through the order gateway) and `killswitch` (`store.set_kill_switch(True)` plus cancelling pending orders). Emit `CONTROL_EXECUTED` only after they succeed. Split the gate out of the telemetry `try`, and make it fail closed: on exception, return HOLD.

### 2.5 🟠 C5: A credential-shaped string in a public repository

`tests/test_section_f_hardening.py:20` contains a 48-hex-digit `ROUTESME_KEY=rm-…` value. The comment above it says the neighbouring `api_key` was replaced with a synthetic one after a real key leaked, but this value does not look synthetic. **Treat it as compromised: rotate the RoutesMe key**, replace the value with an obvious fake such as `rm-TESTFIXTURE…`, and add a secret scanner (`gitleaks` or `detect-secrets`) as a pre-commit hook. `operations/security_audit.py` already exists and could run in CI.

## 3. High findings

### 3.1 🟠 H1: The daily loss limit resets on restart in non-UTC timezones
`core/risk_manager.py`: `__init__` compares against **UTC** (`:97-100`), `reset_daily_limits` stores the **local** date (`:118`), and `set_store` compares against **local** (`:219-220`). In IST (UTC+5:30), between 00:00 and 05:30 every restart sees `state_date (local) != current_date (UTC)` and resets `daily_start_equity`. A tripped daily breaker can be cleared just by restarting. On this Mac that window is about a quarter of every day. **Fix:** `datetime.now(timezone.utc)` everywhere in risk state. Better still, use the **broker server day**, since the trading day is defined by the broker. There are 29 naive `now()`/`today()` calls in 9 production files.

### 3.2 🟠 H2: The harness can't bound a stage
- `StageSpec.timeout_s` (`core/harness/stage_contracts.py:26`) is set on every stage but **never read**. `run_stage` (`pipeline_v2.py:157`) calls `spec.fn` synchronously, so a hung provider or MT5 call stalls the pulse thread indefinitely. (`intelligence/boot_fetch_watchdog.run_stage_with_deadline` already does this correctly for boot; reuse it.)
- `fallback="degrade"` sets `ctx.flags["hold_only"]` (`:215`), but nothing reads it before execution. It only appears in the `CYCLE_SPAN_DONE` telemetry (`:893`).

### 3.3 🟠 H3: A missing module turns a readiness gate into a stub that always passes
`operations/readiness_report.py:60-67`: if `strategy_trial_ledger` can't be imported, which is always the case because the file isn't in the repo, `_verify_chain_cpcv()` becomes `lambda: {"valid": True, "status": "ABSENT"}`. `core/cpcv_backtester.py:95-99` quietly falls back to the other ledger. Three readiness tests fail because of it. The pattern `try: import X / except ImportError: <permissive stub>` appears throughout the codebase. **Rule: a missing safety module must fail closed and be loud.** Either commit `core/strategy_trial_ledger.py` or remove the gate.

### 3.4 🟠 H4: The validator approves when it gets no evidence
`DeterministicValidator.validate` (`core/trading_safety.py:997+`) defaults `clock_ok`, `session_allowed`, `liquidity_ok`, `microstructure_ok` and `required_data_ok` to **True** (`:1015-1021`), and `min_stop_distance` to **0** (`:1034`). Meanwhile `market_open`, `symbol_tradable` and `completed_candle` default to False. Whether a check runs therefore depends on whether the upstream dict happened to include the key. A refactor that drops a key silently disables that gate. **Fix:** declare a typed `MarketEvidence` dataclass with no defaults for gate fields, and reject on any missing field.

### 3.5 🟠 H5: The statistics are inflated before anyone sees them
Re-verified from the previous audit; all still open:
- **Deflated Sharpe never deflates.** `MetricsEngine.compute_summary(backtest_trials=1)` (`core/metrics.py:921`). The only service wrapper (`core/quantitative_metrics_service.py:170`) also defaults to 1, and no caller passes a trial count.
- **Annualization is wrong.** Sharpe and Sortino use `periods_per_year=252` (`core/metrics.py:774, 792, 944`) on per-trade or per-pulse series.
- **Alpha miner is fit in-sample.** `research/alpha_miner/ga_engine.py` has no train/test or holdout split; the final selection is the maximum over about 15k candidates on the same returns.
- **`research/contextual_bandit.py` is not a bandit.** It applies a threshold to a shrunk mean, with no sampling or exploration.
- **`strategy_registry.json`:** 10 entries are at stage **FULL** with hand-written metrics. The file carries an `_EVIDENCE_INVALID` marker, but **no production reader checks it**. `core/autonomous_bootstrap.py:302-307` treats them as active, and the deck displays their Sharpe values.

### 3.6 🟠 H6: Coverage is lowest where money moves
| Module | Coverage |
|---|---|
| `core/order_execution.py` | **40.3 %** |
| `data/market_data_provider.py` | 54.5 % |
| `data/llm_router.py` | 58.0 % |
| `intelligence/llm_orchestrator.py` | 60.3 % (4,485 statements) |
| `core/trade_manager.py` | 64.9 % |
| `core/trading_safety.py` | 83.1 % |
| `operations/autonomy.py` | 90.7 % |

The MT5 bridge (`compat/mt5_bridge`) makes the live path testable on any OS: run the real server code against a fake MT5 module, as `tests/test_mt5_bridge.py` does. Use it to build an end-to-end "proposal → order_send" test with an in-process fake broker.

### 3.7 🟠 H7: The monolith and process model
- `mt5_trader.py: main()` is **4,362 lines**. The `llm-trade` branch alone is about 1,965.
- `LLMOrchestrator.execute_cycle` is **2,039 lines** with **51 exception handlers**, 24 of which swallow to `pass` or debug. `_validate_proposal` is 737 lines; the class has 94 methods.
- 25 production files are over 1,000 lines.
- In one process: market pulse, position management, LLM calls, news triage (a 421M-parameter model), a startup training pipeline (`mt5_trader.py:4296+`), RL, research schedulers and the API sync. `OPERATOR_RUNBOOK.md` §1 documents four native torch crashes caused by memory pressure, and a 1.5 GB free-RAM boot requirement. That is the cost of putting training and trading in one address space.

`pipeline_v2` is the right direction: declared stages, SLAs, events. Finish it (§9).

## 4. Workflow: how a trade actually happens

```
START_TRADING.bat / start_trading.sh
 └─ mt5_trader.py main() ── llm-trade
     ├─ boot: PID file → profile mount (core/harness) → store/risk/orchestrator wiring
     ├─ supervisor kernel → task queue → compliance log → crash recovery
     ├─ AutonomousBootstrap: VALIDATE (readiness, backtest "active" registry strategies) → PREPARE (macro, news, calendar, latch)
     ├─ Startup training pipeline (backtest + training before first trade)        ← slow, RAM-heavy
     ├─ External guardian thread
     └─ loop (per symbol × strategy, ThreadPool):
         pipeline_v2 envelope
          ├─ maintenance stages: velocity.poll → reconcile.pending → reconcile.open → memory.dispatch → position.tick → heartbeat
          └─ execute_cycle()  (llm_orchestrator.py:7336, 2,039 lines)
              autonomy gate (fail-open, C4) → new-candle dedupe → holiday/news safeguards
              → data-quality gate → news-trading gate → feature/macro/causal/auto-tools (~800 lines)
              → provider circuit + LLM budget permit → get_decision() (LLM JSON → HOLD on any parse failure)
              → _validate_proposal() → DeterministicValidator.validate() (H4)
              → sizing (RiskManager) → execution plan + margin preflight → duplicate-intent guard
              → UrgencySOR → place_pending_order() → MT5 (geometry checks in validate_order_params)
```

What works well in this flow:
- Every LLM failure path ends in HOLD (`llm_orchestrator.py:1994-2016`).
- Deterministic fallbacks can never escalate to a trade (`:1971-1975`).
- SL/TP geometry and RR ≥ 2 are enforced right before sending (`core/order_execution.py:192-221`).
- Duplicate order intents are blocked.
- Per-strategy LLM context is now isolated by thread key. The previous audit's #18 is fixed (`:7262-7300`).

Workflow flaws:
1. **The order of work is backwards for latency.** About 800 lines of feature, macro, causal and auto-tool work, plus an LLM call, run *before* cheap deterministic vetoes such as the kill switch, spread, session and stale tick, which only run in the validator. Move every cheap veto to the top of the cycle.
2. **Training at boot delays the first trade** and is the main crash vector. Make training a separate scheduled job that publishes artifacts the engine loads read-only.
3. **Boot depends on fragile machinery:** RAM watchers, a 2-hour duty watcher, guarded boot, a 25-minute triage prompt. That's the symptom of (2). With the hot path in its own small process, most of the runbook goes away.
4. **Paper mode still needs a live MT5 feed**, by design (fail-closed market data). That's correct, but there is no recorded-data replay mode for development. `research/broker_replay.py` exists; wire it in as a `--replay` transport so the full loop can run anywhere.

## 7. UI and UX review

### 7.1 Too many surfaces
| Surface | State | Recommendation |
|---|---|---|
| **OpenTUI deck** (`tui_opentui/`, 21.5k lines, 40 views) | Canonical; typechecks; transport fails closed | Keep it as *the* operator console |
| **React web GUI** (`gui/`, 13 components) | Partly live, partly mock (M11); hard-coded URL (M10) | Either make it a read-only remote viewer or retire it |
| Tkinter/customtkinter (`ui/gui_dashboard.py`, `gui_launcher.py`), pywebview (`ui/main_window.py`) | Legacy | Retire |
| HTML dashboards (`ui/alpha_dashboard.py`, `compliance_dashboard.py`, `visualizer/`) | Generated reports | Keep as reports, linked from the deck |
| 6 "RETIRED" stubs (`ui/tui.py`, `tui_dashboard.py`, `unified_tui.py`, `settings_tui.py`, `display.py`, `log_monitor.py`) | Print a pointer to the deck | Delete |

### 7.2 Deck information architecture
- **40 views in 6 sections**, navigated by digit keys that mean *section* at the top level, *view* inside a section, and *tab* inside some screens (e.g. MT5Screen binds 1-4). That's a classic mode error, and it caused the earlier MT5 "press 3" crash. Make the `/` command palette the primary way to navigate, keep digits for sections only, and use `Tab`/`[ ]` inside screens.
- **Consolidate to about 12 views:** Market (feed + cockpit + positions), Journal, Approvals, Brain (brain + deliberation + causal + fusion), Macro, Strategies (strategies + lifecycle + observatory + research pipeline + validation), Backtest/Alpha, Models/RL, Autonomy & Risk, Health (health + metrics + diagnostics + logs + data sources), MT5, Settings. The system map and pipeline graph are developer views; move them behind a `dev` toggle.
- **Add a persistent safety strip on every screen:** `PAPER | LIVE` (high-contrast colour), autonomy level, kill switch and latch state, daily P&L against the daily limit, feed age, MT5 bridge status, LLM provider circuit. Today this information is spread across Cockpit, Autonomy, Health and MT5.

### 7.3 Dangerous actions and honest feedback
- **Typed confirmations for irreversible actions:** a live start (type the account number), flatten, kill switch, a manual order (C3), and a strategy promotion to FULL. Show exactly what will happen ("close 3 positions, 1.2 lots, est. P&L −$84").
- **Feedback must report outcomes, not intents.** `CONTROL_EXECUTED` for a no-op (C4) is the worst case: the operator thinks positions are flat. Show the states *requested → acknowledged → applied (n positions closed)*.
- **Don't display numbers you can't back up.** The registry's FULL strategies (H5) and the GUI's mock history (M11) show fabricated Sharpe and P&L next to real data. Hide anything without evidence, or badge it `UNVERIFIED`.

### 7.4 Web GUI specifics
Split the 618 kB bundle (lazy-load `recharts` views). Add an empty state for "engine not running" instead of zeros. Route all calls through one API client that carries the auth token from §2.2.

## 9. Target architecture

The aim is a smaller, more boring, more honest core. It uses components that already exist (`pipeline_v2`, the event bus, `TradingStore`, the boot-fetch watchdog, the MT5 bridge).

```
┌────────────────── execution kernel (small process, always on) ──────────────────┐
│  market feed ─▶ cheap vetoes ─▶ pipeline_v2 stages (real deadlines) ─▶          │
│  DecisionClient (LLM, async, deadline, HOLD on miss) ─▶ Validator(MarketEvidence)│
│  ─▶ RiskManager(UTC/broker day) ─▶ OrderGateway ─▶ MT5 (native or bridge)        │
│  OrderGateway is the ONLY caller of order_send. Journal write-ahead, idempotent. │
└─────────────▲──────────────────────────────▲──────────────────────────▲──────────┘
              │ read-only artifacts          │ events (SQLite outbox)    │ authed API
┌─────────────┴────────┐   ┌─────────────────┴────────┐   ┌──────────────┴─────────┐
│ research/training    │   │ news + macro worker      │   │ API server (token, CORS│
│ worker (cron/launchd)│   │ (triage model lives here)│   │ allowlist, Host check) │
│ backtests, RL, GA,   │   │ publishes latch + scores │   │ deck / web GUI         │
│ promotion proposals  │   │                          │   │                        │
└──────────────────────┘   └──────────────────────────┘   └────────────────────────┘
```

1. **Packaging:** add a `pyproject.toml` and make `llm_trader` an installable package (`pip install -e .`). Remove every `sys.path` insert. Fixes C1 and M1.
2. **One order gateway** that all order paths (engine, UI, MCP, emergency flatten) go through. It writes the journal before sending and reconciles after. Fixes C3 and part of C4.
3. **Process split:** the kernel holds no torch, no training and no triage model. Workers publish versioned, read-only artifacts. This removes the RAM boot requirement and the crash class in H7.
4. **Finish `pipeline_v2`:** break `execute_cycle` into the stage functions it already marks with `_v2_stage_start`. Run each stage under `run_stage_with_deadline` and honour `hold_only`. Fixes H2.
5. **Typed contracts:** use dataclasses (or pydantic) for `MarketEvidence`, `LLMDecision` and `Settings` (all 117 env flags, validated at boot). Fixes H4, M3 and M5.
6. **Persistence:** add a repository layer over a single journal DB with numbered migrations; derived caches go in separate files. Fixes M2.
7. **Honest statistics:** a trial counter written by every backtest, used by DSR; annualize from bar duration; purged walk-forward split for the GA. Fixes H5.
