19 19. Persistence: Databases, Schemas & State Files

The doctrine. trading_state.db is the authoritative journal. Every other database is operational (agent tasks, events, alerts), and every JSON state file is a cache or policy that can be rebuilt from the journal. Deleting a JSON file loses speed; deleting the journal loses history.

19.3 JSON / JSONL state files

core/state_persistence.py defines StoreBackedState: modules declare a store_key and their state is persisted in the journal's state table, with atomic file writes (core/file_utils.safe_atomic_write_json) as the on-disk mirror. state_manager.migrate_json_states_to_store() migrates legacy files into the store at boot (mt5_trader.py ~3844–3846).

Two ledgers, one truth. The JSON files and the journal can momentarily disagree after a hard kill. The system resolves this in a fixed direction: reconciliation compares broker → journal (§06.6), and the JSON mirror is refreshed from the store on the next write. If a JSON file is deleted, the state is rebuilt from state; if the journal is damaged, operations/journal_audit.py (§21) and the encrypted backups (operations/journal_backup.py) are the recovery path.
