18.1 The model registry

The journal owns a model_registry table (core/trading_safety.py ~248–257):

CREATE TABLE IF NOT EXISTS model_registry (
  id INTEGER PRIMARY KEY, model_key TEXT NOT NULL, version TEXT NOT NULL,
  kind TEXT NOT NULL, status TEXT NOT NULL DEFAULT 'CANDIDATE',
  feature_schema_version TEXT, training_data_hash TEXT,
  metrics TEXT NOT NULL, artifact_uri TEXT, created_at TEXT NOT NULL,
  reviewed_at TEXT, reviewed_by TEXT, review_note TEXT,
  UNIQUE(model_key, version)
);
CREATE INDEX IF NOT EXISTS idx_model_registry_status ON model_registry(model_key, status, created_at);

Three fields make promotion auditable: feature_schema_version (which features it was trained on), training_data_hash (which data) and status (default CANDIDATE). Reviews record reviewed_at/reviewed_by/review_note, and the CLI enforces the vocabulary APPROVED | REJECTED | RETIRED | ROLLED_BACK (mt5_trader.py journal model-register / model-review).

The invariant: the factory may demote its own work, but it can never self-approve live authority. Promotion to paper is automatic; promotion to micro/live is a human act recorded in the journal.

18.4 Portfolio governance

Beyond per-strategy governance the book is governed as a portfolio: core/hierarchical_portfolio.py (layered allocation across sleeves), core/portfolio_decorr.py (decorrelating sleeves), research/qubo_rebalancer.py and research/risk_parity_engine.py (rebalancing objectives), core/alpha_capacity.py (capacity limits), and operations/account_growth.py with core/account_sizing.py (capital-growth policy). The P8 allocation cap (§05.7) is where this governance touches a single order: it can only reduce volume.
